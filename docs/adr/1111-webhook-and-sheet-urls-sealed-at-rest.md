# 1111. Webhook and sheet-sync URLs sealed with APP_SECRET_KEY; plaintext with a warning without it

- Status: Accepted
- Date: 2026-11-07

## Context
`workspace_webhooks.url` (C-L13) embeds the Slack/Discord bearer secret, and
`collection_sheet_syncs.url` can carry a sheet's sharing key. The server has to use the raw URL,
so hashing is not an option. docs/adr/1061-* introduced `APP_SECRET_KEY` and `secretBox.ts` and
anticipated this use. The key is optional: many installs run without it.

## Decision
- **Sealed in place.** The `url` column keeps its name and holds `v1.<iv>.<tag>.<ct>` (AES-256-GCM,
  purpose `webhook-url` / `sheet-sync-url`, AAD = webhook id / page id) when the key is set. No
  schema change. A URL never starts with `v1.`, so sealed and plaintext rows are told apart without
  a flag. The webhook id is generated by the route before the insert so it can be the AAD.
- **Reading** goes through one helper (`hookUrl`, `syncUrl`; `revealSecret`): plaintext passes
  through, sealed is opened. The masked URL in the list and in audit labels is computed from the
  opened value (`••••` when it cannot be opened).
- **Without `APP_SECRET_KEY`: plaintext + warning, nothing restricted.** Existing key-less installs
  keep working unchanged; new URLs are stored as given. Boot logs the number of plaintext values.
  Restricting webhooks to keyed installs was rejected: it would silently stop notifications that
  work today, for a Low finding.
- **Key added later**: the boot pass (`migrateSecretsAtRest`, docs/adr/1110-*) seals every
  plaintext URL. Idempotent (`url NOT LIKE 'v1.%'`).
- **Key removed or changed** after sealing: delivery fails with the non-retryable error
  "URL cannot be decrypted: APP_SECRET_KEY is missing or changed" (it counts towards the
  auto-disable streak like any failed delivery) and a sheet sync reports the same in its status.
  The boot log counts sealed rows only when the key is unset; a changed key is noticed at first use.
  Re-adding the webhook or saving the sync settings again re-seals.

## Consequences
- C-L13 is fixed for installs with `APP_SECRET_KEY`; without it the URLs stay in plaintext and the
  boot log keeps saying so.
- Rolling back to v0.4.0 after sealing: webhooks fail ("invalid URL") and sheet syncs fail until
  the URLs are entered again (or the pre-upgrade backup is restored).
- No key rotation (same as 1061).
- Tests: `secretsAtRest.db.test.ts` (legacy plaintext delivered after the pass, new URLs sealed,
  key-less mode, unreadable error).
