Inkling API Contract (M1)

The REST contract shared by the web app, scripts and the MCP tools.

Rendered from docs/API.md in the repository. Markdown source

The shared contract between the server and web agents. This document is the source of truth: implementations must not diverge from it. Request validation schemas and DTO types are defined in @inkling/shared (packages/shared/src/index.ts), and both sides import them. 한국어: API.ko.md.

Common rules

  • Every REST endpoint uses the /api prefix with JSON in and out. Exceptions: GET /files/:id (binary), WS /collab (Hocuspocus).
  • Authentication: session cookie inkling_sid (httpOnly, SameSite=Lax, Path=/, 30 days, Secure when COOKIE_SECURE=1). The server stores only the SHA-256 of the token (docs/adr/1060-*).
  • Cross-site check: a non-GET/HEAD/OPTIONS /api request without an Authorization header whose Origin (else Referer) is not PUBLIC_URL/APP_URL → 403 CROSS_SITE_REQUEST. Clients sending neither header (CLI, curl) are allowed. The /collab WebSocket upgrade is checked the same way (docs/adr/1062-*).
  • Error response format: { "error": { "code": string, "message": string } } (ApiErrorBody).
    • Codes: UNAUTHORIZED(401), FORBIDDEN(403), NOT_FOUND(404), VALIDATION(400), EMAIL_TAKEN(409), INVALID_CREDENTIALS(401), INVALID_CODE(404), INVALID_RESET(400), EMAIL_NOT_VERIFIED(403), DELEGATED_ACCOUNT(400), RATE_LIMITED(429, Retry-After), MAIL_DISABLED(501), MAIL_FAILED(502), CROSS_SITE_REQUEST(403), INVALID_TOTP_CODE(401), TOTP_CODE_REUSED(401), TOTP_CHALLENGE_EXPIRED(401), TWO_FACTOR_ALREADY_ON(409), TWO_FACTOR_UNAVAILABLE(501), PAYLOAD_TOO_LARGE(413), UNSUPPORTED_TYPE(415), INTERNAL(500).
    • message is English. Clients localize by code; the web app translates known codes (and some exact messages) and falls back to message otherwise. Do not match on message text.
  • Permission model: every workspace operation requires being a member. Pages and files are authorized through the workspace they belong to.

Localization

  • Supported locales: en, ko. The operator can set DEFAULT_LOCALE (en | ko; the server falls back to en when it is unset).
  • The web client sends Accept-Language: <ui locale> on every API request.
  • Server-generated content (built-in templates, default titles of pages the server creates such as the Tasks document, default collection fields and views, the sign-up workspace name) uses the user's saved locale, else Accept-Language, else DEFAULT_LOCALE.
  • Emails use the recipient's saved locale, else DEFAULT_LOCALE.
  • Error messages are not localized (see Common rules).
  • Related endpoints: GET /api/auth/mode (defaultLocale), GET /api/auth/me (user.locale), PATCH /api/auth/me/locale (see Auth).

Collab (real-time co-editing)

  • WS /collab: Hocuspocus protocol. documentName = page UUID.
  • Authentication: the session is determined from the upgrade request's cookie (the provider's token value is ignored, but the client sends a dummy token: 'cookie' so Hocuspocus runs the onAuthenticate hook).
  • Authorization: documentName must be a UUID, a live page, and the user must be a member of its workspace. Otherwise the connection is refused.
  • Persistence: Yjs state is saved to page_docs.state (bytea) with a debounce (2s, max 10s). Saving also updates pages.updated_at.

Misc

  • GET /api/health → { ok: true } (no auth required)
  • Every /api response carries X-Inkling-Build: <id> (the id in WEB_DIST/build.json; absent when unknown). A client whose own build differs shows the update banner or reloads (docs/adr/0990-0993).
  • GET /api/version → { build: string | null, version: string, updateMode: 'prompt' | 'force' } (no auth required)
  • GET /api/version/latest (admin) → { enabled, current, latest: { version, url } | null, updateAvailable }; enabled: false unless UPDATE_CHECK=github (docs/adr/0994-*)
  • Production (Docker): serves WEB_DIST statically + SPA fallback (GET requests outside /api, /files, /collab → index.html)

M2 additional contract (Markdown round-trip · wiki links · trash · search)

Wiki link representation (convention shared by server and web)

  • Wiki links in documents are standard BlockNote link inlines whose href is an internal path: /w/<workspaceId>/p/<pageId> (no custom inline type, so Markdown conversion and server parsing work without extending the schema).
  • On Markdown export, internal links become [[Title]] (title = link text).
  • On Markdown import, [[Title]] is resolved to an internal link by title match: ① pages in the same import batch ② live pages in the workspace (case-insensitive, most recent updatedAt first). Unresolved links stay as the literal text [[Title]].
  • Backlink index: on document save (store), internal href patterns are extracted from the blocks and page_links(source_page_id, target_page_id) is synced (delete all then reinsert, distinct, self-references excluded; the store itself succeeds even if this fails).

Page kinds (kind) — M2

  • pages.kind: 'doc' | 'folder' | 'canvas' (default doc). createPageSchema gains kind? and title?.
  • folder: no document (no collaboration connection). Used to organize the tree. Exported as a directory only; on import, a directory without a Markdown file → a folder page.
  • canvas: implemented in M3.5 (JSON Canvas). The M2 server only needs to store and return kind.
  • PageMetaDTO includes kind, returned in every page response.

M3 contract — Collections (Notion-style databases)

Types and validation schemas come from the M3 section of @inkling/shared (collectionFieldSchema, viewConfigSchema, updateFieldsSchema, createViewSchema, updateViewSchema, updatePropsSchema, CollectionDTO, CollectionViewDTO, RowDTO).

Model

  • A collection = a page with kind='collection'. Field definitions live in collections (pageId pk, fields jsonb), views in collection_views.
  • A row = a live child page of the collection page (kind is usually doc). Property values are in pages.props jsonb { fieldId: value }.
  • Value shapes: text/url→string, number→number, checkbox→boolean, date→'YYYY-MM-DD' string, select→optionId string, multiSelect→optionId string[], person→userId string.
  • The page tree (GET pages) also returns the collection's children (rows) as-is; the web app hides them when assembling the tree if the parent is a collection.

M8 contract — Invite links · member management · version history

Invites

  • GET /api/workspaces/invite-preview?code=<code> (authentication only, membership not required) → InvitePreviewDTO { name, icon, memberCount }. Unknown code 404 INVALID_CODE.

Members (roles owner | admin | member, docs/adr/0945-*)

  • PATCH /api/workspaces/:id/members/:userId body updateMemberSchema { role: 'owner'|'admin'|'member' } (owner only) → { member: MemberDTO }. Demoting the last owner 400.
  • DELETE /api/workspaces/:id/members/:userId → 204. An owner removes anyone, an admin removes plain members (owner/admin target 403), or you leave. The last owner leaving 400, unless they are the only member and send { name } (the workspace's name) from a browser session: then the workspace is deleted at once (0.22, v0.22.0 additions). On removal, that user's private pages in this workspace are soft-deleted (audit L3), their document ownerships are cleared and (when someone else is removed) the invite code is regenerated.
  • GET /api/workspaces/:id/member-candidates, POST /api/workspaces/:id/members: only callers the member-add policy allows (default owners and admins; 403 otherwise, docs/adr/0948-*).
  • POST /api/workspaces/:id/invite/regenerate (owner or admin) → { workspace: WorkspaceDTO } (new code).
  • POST /api/workspaces/:id/transfer (owner) body transferOwnershipSchema { userId } → { members: MemberDTO[] }. The target becomes owner and the caller becomes member in one transaction under the ws-members lock (docs/adr/0911-*). Not a member (delegated accounts included as usual) 400; the caller themself 400; caller not an owner 403 (also the loser of two concurrent transfers). Afterwards the old owner can leave normally.

Workspace deletion (owner, soft delete with a 30-day restore — docs/adr/0910-*)

  • GET /api/workspaces/:id/delete-preview (owner) → WorkspaceDeletePreviewDTO { pages, files, publicLinks, members, restoreDays } for the confirm dialog.
  • DELETE /api/workspaces/:id body deleteWorkspaceSchema { name } → 204. name must equal the workspace name (surrounding spaces ignored, case-sensitive), else 400; member 403; not a member / unknown / already deleted 404. Takes effect for everyone at once: the workspace disappears from GET /api/workspaces, every /api/workspaces/:id/*, page, comment, file (/files/:id) and template route answers 404, public links (/api/public/*; /s/* falls back to the plain app shell) and the invite code stop working, the iCal feed drops its items, query blocks, MCP tools, reminders, webhooks and sheet sync skip it, and open collaboration sockets are closed. Other members get a workspace_deleted notification with the workspace name (no webhook is sent).
  • GET /api/workspaces/deleted → { workspaces: DeletedWorkspaceDTO[] } — workspaces the caller owns that are deleted and still restorable (deletedAt, purgeAt = deletedAt + WORKSPACE_RESTORE_DAYS, 30 by default), newest first. DELETE /api/me answers a wrong two-step code with 400 INVALID_TOTP_CODE (sign-in answers 401).

OAuth routes answer in the OAuth error format ({ error, error_description }):

  • POST /oauth/register answers 503 temporarily_unavailable in two cases: the instance storage fuse is tripped (checked first), or OAUTH_UNUSED_CLIENT_MAX is reached and every never-used client is younger than 15 minutes (with Retry-After: 60). Under the cap a registration first deletes the oldest never-used clients.
  • A self-registered client deleted by OAUTH_UNUSED_CLIENT_HOURS or OAUTH_UNUSED_CLIENT_MAX is an unknown client: the authorization step answers 400 INVALID_CLIENT ("Unknown app. Connect again from the app.") and the app has to register again (docs/adr/2536-*). Only clients nothing points at are deleted, so a client with a code or a grant never meets this.
  • On every server, POST /oauth/token with grant_type=authorization_code consumes the code and stores the grant in one transaction; the answers are unchanged.

v0.22.1 changes

No route added or removed, no migration (docs/adr/2540-* .. 2551-*). What a client or an integration can notice:

  • Usage (GET /api/workspaces/:id/usage): with LIMIT_WORKSPACE_STORAGE_MB, storageBytes also counts the rows of the search and section indexes, and every file as max(size, 4,096) + 1,024 bytes (in fileBytes too). It is the cached count, which can hold estimates of saves that no recount has seen yet: 2 bytes per byte a body grew, for its index rows, until a recount after the index pass (docs/adr/2545-, 2548-). Without the setting both are counted as in 0.22.0.
  • 413 LIMIT_STORAGE to a page guest of the workspace carries the code and the message only, without limit, used and unit (docs/adr/2547-*). Members still get them. The collaboration socket never sends the numbers.
  • PATCH /api/pages/:id with a storage limit checks membership and edit rights before storage: someone who may only read the page gets the 403 of the edit check, not a 413 (docs/adr/2547-*).
  • Audit events: page.access_granted, page.access_changed, page.access_removed and the grant of an accepted page invitation store personId beside person. GET /api/workspaces/:id/audit leaves personId out, as it does the other id keys. Account deletion by the person or by expiry sets person and personId to null where personId is the account's id, and sets email to null in page.guest_invited rows whose address is the account's own sign-in email or ID.
  • Collaboration socket, storage (only with LIMIT_WORKSPACE_STORAGE_MB or LIMIT_INSTANCE_STORAGE_MB):
    • An update that does not fit is not applied; the connection becomes read-only, gets the stateless message {"t":"storage","why":W} and is closed with code 4000 storage-full. W is "workspace" (the workspace's room), "page" (the page body's cap), "structs" (new: the page would pass 300,000 Yjs structures, docs/adr/2540-*) or "instance" (the fuse). The provider reconnects and gets the read-only scope. After "workspace" or "page" the page opens read-only for 10 minutes or until a recount finds room, after "structs" for the 10 minutes, and after "instance" while the fuse is tripped.
    • When a save or a recount takes the workspace over its limit, or a page body over its cap, every editing connection gets {"t":"storage","why":"workspace"} or {"t":"storage","why":"page"} and the same close 4000 storage-full (before 0.22.1: close 4403 permission-changed, after which the web app did not reconnect). When a recount finds room, read-only connections are closed with 4000 and come back with the read-write scope. 4403 stays for access that changed.
    • An update is admitted while cached count + 3 × (unsaved growth + the update) + the next version copy fits; the unsaved growth is what the document took in, so re-sending an update it already holds adds nothing (docs/adr/2543-, 2548-).
  • Collaboration socket, every server (docs/adr/2541-, 2542-, 2544-*), for anyone who writes a client:
    • The inbox document (inbox:<userId>) is authorised read-only. A Sync update or sync step 2 to it that carries a structure or a deletion is refused and the socket is cut; only the empty step 2 passes. The server's stateless notices on it are unchanged.
    • Awareness: a document connection may bring at most 4 client ids of its own into the document (an id counts against the connection whose message added it while the document had no state for it; resending other clients' states, as the Hocuspocus provider does, never counts), a socket may add new client ids 64 at once and then one a second, a document holds at most 1024 ids, a state at most 16 KB, a message at most 1 MB, the states a socket's connections brought in at most 256 KB together, and a socket may change 128 KB of states at once and then 16 KB a second (entries that change nothing are free). A message past one of the two rates (new ids, changed states) is dropped: not applied, not sent on, and the socket stays; the next state replaces it. A message past one of the other caps is never applied and the socket is cut. The ids a closed connection brought in are removed.
    • A cut socket is terminated without a close frame (a browser reports 1006); the provider reconnects.
    • At most 40 sockets per client address (a constant, MAX_CONN_PER_IP in collab.ts), with an IPv6 /64 counted as one address; past it the upgrade answers 429.
  • Replace (POST /api/pages/:id/content with replace, update_page and patch_section with replace, patch_sections, reverts; every server, docs/adr/2550-*): when the old and new blocks of the range hold more than 128 KiB of characters together, the edit has a budget (2,000 Yjs text operations, 40 million diff steps). Past it, a changed block keeps its id, colors, alignment and toggle and its content is replaced whole. The answer is unchanged. Ranges up to 128 KiB are edited exactly as before.
  • AI steps (GET /api/pages/:id/snapshots, step): an agent's update_page replace has no added and removed when the new body has more than 2,000 blocks or more than 262,144 characters of Markdown, as when the page had more than 2,000 blocks before (docs/adr/2551-*).
