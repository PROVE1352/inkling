그 밖의 문서

데모 인스턴스 운영하기

이 문서는 저장소의 docs/DEMO.ko.md을 그대로 옮겼습니다. Markdown 원문

낯선 사람에게 여는 공개 데모는 0.22.1 이상에서, 데이터를 전용 파일시스템(0단계)에 두었을 때만 여세요. 0.22.0에는 데모가 같은 기계의 다른 서비스와 디스크와 메모리를 같이 쓸 때의 문제가 남아 있었고(LIMITS-37부터 LIMITS-42까지) 0.22.1이 고쳤습니다. 아직 알려진 문제는 KNOWN-ISSUES.ko.md의 "0.22.1에서 추가"에 있습니다. 0.22.0으로 이미 띄운 데모는 먼저 옮겨야 합니다(아래 "0.22.0 데모 옮기기").

데모 인스턴스는 처음 보는 사람도 가입해서 써 볼 수 있게 따로 띄우는 Inkling 서버입니다. 운영 중인 서버 옆에서 돌지만 나눠 쓰는 것은 없습니다. compose 프로젝트, 데이터베이스, 볼륨, 네트워크, 포트가 모두 따로입니다. 0.22의 제한 모드가 이런 서버에 필요한 것을 켭니다. 이메일 대신 아이디로 가입, 전체 계정 수 상한, IP별·시간당 가입 횟수 제한, 가입 14일 뒤 계정 삭제, 워크스페이스·멤버·페이지·저장 용량 한도, 서버 전체의 저장 공간 퓨즈, 밖으로 데이터를 보내는 기능을 서버 전체에서 끄는 스위치, 가입할 때 약관 동의, 모든 화면의 "Demo" 표시가 그것입니다. 데이터는 크기와 inode 수가 따로 정해진 전용 파일시스템에 두므로 본 인스턴스가 쓰는 디스크를 채울 수 없습니다(0단계). English: DEMO.md.

파일은 deploy/demo/에 있습니다. demo.sh(데모를 띄우고 내리고 확인하는 유일한 방법), compose.demo.yaml(compose.yaml에 덧씌우는 파일), demo.env.example(설정), legal/(이용약관, 개인정보 처리방침, 가입 화면 문구의 틀)입니다. 설계 설명은 ADR 2500–2551에 있습니다.

0. 데모 데이터용 파일시스템 만들기

처음 up을 하기 전에 서버에서 만듭니다. 데모의 데이터베이스, 업로드, 백업, 백업 제어 파일은 경로 하나(DEMO_VOLUME_ROOT) 아래의 폴더 네 개(db, data, backups, backup-ctl)에 들어갑니다. 그 경로에 데모만 쓰는 파일시스템을 마운트합니다. 저장 공간 퓨즈(LIMIT_INSTANCE_STORAGE_MB)는 WAL, 백업, 로그를 보지 못하고, 넘친 뒤에야 끊깁니다. 데모 사용자가 본 인스턴스의 디스크를 채우지 못하게 막는 것은 크기가 정해진 파일시스템입니다. deploy/demo/demo.sh up은 DEMO_VOLUME_ROOT가 루트 파일시스템(또는 Docker 데이터 폴더가 있는 파일시스템) 위에 있으면 거절합니다.

이 일은 운영자가 서버에서 root로 직접 합니다. 이 문서와 스크립트는 파일시스템을 만들거나 마운트하거나 지우지 않습니다. Linux에서는 이미지 파일에 ext4를 만들고 부팅할 때마다 마운트하는 방법이 있습니다.

sudo fallocate -l 30G /var/lib/inkling-demo.img     # takes the 30 GB at once (not a sparse file)
sudo mkfs.ext4 -F -m 0 -N 600000 -E nodiscard -L inkling-demo /var/lib/inkling-demo.img   # nodiscard: mkfs would otherwise give the space back
sudo mkdir -p /srv/inkling-demo-data
sudo chattr +i /srv/inkling-demo-data               # the empty mount point: nothing can be created in it while unmounted
echo '/var/lib/inkling-demo.img /srv/inkling-demo-data ext4 loop,nodev,nosuid,noexec,nofail 0 2' | sudo tee -a /etc/fstab
sudo mount /srv/inkling-demo-data
sudo mkdir -p /srv/inkling-demo-data/db /srv/inkling-demo-data/data /srv/inkling-demo-data/backups /srv/inkling-demo-data/backup-ctl
findmnt /srv/inkling-demo-data && df -h /srv/inkling-demo-data && df -i /srv/inkling-demo-data
sudo du -h /var/lib/inkling-demo.img                  # the full size, not a few MB: the image really holds its space

그다음 demo.env에 DEMO_VOLUME_ROOT=/srv/inkling-demo-data를 적습니다. 따로 둔 디스크, 파티션, LVM 볼륨, 가상 머신도 됩니다. 재부팅한 뒤에는 deploy/demo/demo.sh up 전에 findmnt로 마운트되어 있는지 확인합니다. 마운트되지 않은 빈 폴더는 루트 파일시스템에 있으므로 up이 본 디스크에 쓰지 않고 거절합니다.

재부팅은 demo.sh를 기다리지 않습니다. Docker가 데모 컨테이너를 스스로 다시 띄우므로(compose.yaml의 restart: unless-stopped) up의 검사가 돌지 않습니다. 파일시스템의 마운트가 실패했다면, 데모가 루트 디스크에 쓰지 못하게 막는 것은 빈 마운트 지점에 폴더 네 개가 없다는 사실뿐입니다. 볼륨이 그 폴더들을 연결하는 것이라서 연결이 실패하고 컨테이너가 뜨지 않을 것입니다(리눅스에서 해 보지 않았습니다, KNOWN-ISSUES LIMITS-51). 위 명령의 두 가지가 이 경우를 위한 것입니다. nofail은 이미지를 마운트하지 못해도 서버가 부팅을 마치게 하고(없으면 마운트 실패가 서버 전체의 부팅을 멈출 수 있습니다), 빈 마운트 지점의 chattr +i는 Docker를 포함해 누구도 루트 디스크의 그 폴더 안에 폴더를 만들지 못하게 합니다(마운트 지점을 지울 일이 생기면 먼저 chattr -i). 그러니 파일시스템이 마운트되지 않은 동안에는 db, data, backups, backup-ctl을 만들지 말고, 재부팅할 때마다 findmnt를 확인하고, 계획한 재부팅 뒤 데모를 직접 띄우고 싶으면 그 전에 deploy/demo/demo.sh down을 실행합니다(데이터는 남습니다).

크기는 퓨즈 + WAL 2 GB + 백업 벌 수 × 퓨즈 + 여유입니다. 프리셋(LIMIT_INSTANCE_STORAGE_MB=3000, 매일 백업 7벌)이면 3 + 2 + 7 × 3 = 26 GB이고, 여유를 두어 30 GB입니다. 퓨즈나 백업 벌 수를 바꾸면 크기도 맞춰 바꿉니다. inode는, 프리셋에서 세는 파일이 많아야 워크스페이스 100개 × 10 MB / 5 KB(파일 하나는 적어도 5 KB로 셈), 약 205,000개이고 여기에 데이터베이스와 백업의 파일이 더해집니다. -N 600000은 inode 수를 묶으면서 그만큼의 여유를 둡니다.

이런 파일시스템 없이 노트북에서 시험해 볼 때만 DEMO_ALLOW_SHARED_DISK=1 deploy/demo/demo.sh up으로 경고를 띄우고 진행할 수 있습니다. 공개 데모에서는 절대 쓰지 않습니다. macOS에서는 디스크 이미지가 실제 디스크처럼 동작합니다(hdiutil create -size 2g -fs APFS -volname demo demo.dmg 다음 hdiutil attach -mountpoint <폴더> demo.dmg).

1. 별도 인스턴스로 띄우기

데모는 따로 만든 폴더에서 배포합니다. 같은 릴리스를 한 번 더 받은 사본이어야 하고, 운영 인스턴스를 실행하는 폴더를 쓰면 안 됩니다(그 폴더의 .env와 평소 명령은 운영용입니다). 같은 서버에서 돌려도 됩니다.

git clone <the Inkling repository> /srv/inkling-demo/inkling    # a second copy, at the release you run
cd /srv/inkling-demo/inkling
cp deploy/demo/demo.env.example deploy/demo/demo.env
# fill in DEMO_POSTGRES_PASSWORD and DEMO_APP_SECRET_KEY (new values, see "Secrets" below),
# PUBLIC_URL: the public https address people will use (for example https://demo.example.com)
# and DEMO_VOLUME_ROOT: the filesystem of step 0
deploy/demo/demo.sh config     # check what would run; changes nothing
deploy/demo/demo.sh up         # builds the demo's own image (DEMO_IMAGE) the first time

데모 명령은 모두 deploy/demo/demo.sh(config, up, build, down, destroy, ps, logs, exec)로 실행하고, docker compose를 직접 부르지 않습니다. 스크립트는 언제나 프로젝트 이름 inkling-demo, compose 파일 두 개, deploy/demo/demo.env(다른 파일은 --env-file로)를 쓰고, 셸의 변수는 PATH, HOME, Docker 연결 변수 말고는 넘기지 않습니다. 셸에 COMPOSE_PROJECT_NAME, COMPOSE_FILE, INKLING_DATA_NAME이 있으면 바로 멈춥니다. up, down, destroy 전에는 해석된 설정을 읽어서, 프로젝트가 inkling-demo이고 모든 볼륨과 네트워크 이름이 inkling-demo_…이고 데이터베이스와 그 역할이 inkling_demo이고 3000번 포트(운영의 기본값)가 없을 때만 진행합니다. 하나라도 어긋나면 아무것도 하지 않고 거절합니다. config는 같은 검사 결과를 보여 주고, up은 CHANGE-ME가 남은 비밀 값도 거절합니다. 앱 이미지는 데모 전용 이름(DEMO_IMAGE, 예시는 inkling-demo:local)이어야 합니다. 이름에 demo가 없거나 운영의 ghcr.io/prove1352/inkling이면 거절하므로, 데모를 빌드하거나 받아도 본 인스턴스가 다음 up에서 쓸 이미지는 바뀌지 않습니다. 볼륨은 모두 절대 경로로 적은 DEMO_VOLUME_ROOT 아래의 폴더여야 하고, up 전에 그 폴더가 전용 파일시스템(0단계) 위에 있어야 합니다. up이 그 안에 폴더 네 개를 만듭니다. 이 이름들은 compose.demo.yaml에 글자로 적혀 있어서 운영 인스턴스가 쓰는 변수로는 데모를 운영 데이터로 돌릴 수 없고, 덧씌우는 파일을 docker compose로 직접 쓰면 안내와 함께 멈춥니다. 데모 설정은 모두 필수라서 운영용 .env로 한도 없는 데모가 뜨는 일도 없습니다. down은 데모의 볼륨을 남기고, destroy는 프로젝트 이름을 직접 입력해야 볼륨까지 지웁니다(아래 "예고 없이 데모를 닫을 때"). 앱은 127.0.0.1:3100(DEMO_PORT)에서만 듣습니다. 3단계 전까지는 밖에서 열 수 없습니다.

새 릴리스로 올릴 때는 데모 폴더에서 git pull(또는 그 릴리스를 체크아웃)한 뒤 deploy/demo/demo.sh build와 deploy/demo/demo.sh up을 차례로 실행합니다. up만 하면 전에 빌드한 이미지를 계속 씁니다.

열기 전에(3단계의 프록시 전에) 서버에서 DEMO_ALLOW_SHARED_DISK 없이 deploy/demo/demo.sh config와 deploy/demo/demo.sh up을 실행합니다. 둘 다 ok 줄만 내고 통과해야 하고, up은 ok DEMO_VOLUME_ROOT is a filesystem of its own을 찍어야 합니다. up이 DEMO_VOLUME_ROOT를 거절하면 0단계를 바로잡고, 그 설정으로 우회해서 진행하지 않습니다.

비밀 값

데모의 비밀 값은 새로 만들고, 운영 인스턴스의 값을 복사하지 않습니다. 두 인스턴스의 로그인과 토큰이 서로 통하지 않는 것은 이 값들이 다를 때뿐입니다.

openssl rand -base64 32    # DEMO_POSTGRES_PASSWORD
openssl rand -base64 32    # DEMO_APP_SECRET_KEY
openssl rand -base64 32    # DEMO_BACKUP_PASSPHRASE, only if BACKUP_RCLONE_REMOTE is set

데모 전용 이름이라서 셸에 내보내 둔 운영 값이 섞여 들어가지 않습니다.

운영자 계정이 생기기 전(4단계)에는 설정 링크로 하는 가입 말고는 어떤 가입도 받지 않습니다. 가입 상한, 계정 수명, 아이디 가입 가운데 하나라도 켜져 있고 관리자가 없는 서버는 다른 가입을 모두 SETUP_REQUIRED로 거절하고, 가입 화면에는 운영자를 기다린다는 안내만 보입니다. 그래서 단계의 순서와 상관없이 처음 온 낯선 사람이 관리자가 되는 일은 없습니다.

2. 약관 폴더 채우기

운영자를 포함해 누구든 가입하기 전에 합니다. 모든 사람은 폴더의 버전에 동의하고, 나중에 고치면 모두 다시 동의해야 합니다.

deploy/demo/legal/은 자리표시자 네 개가 들어 있는 틀입니다. {{OPERATOR_NAME}}, {{CONTACT_EMAIL}}, {{SERVICE_URL}}, {{EFFECTIVE_DATE}}입니다. 저장소 밖으로 복사해서 채우고, demo.env의 DEMO_LEGAL_DIR이 그 사본을 가리키게 합니다.

sudo mkdir -p /srv/inkling-demo && sudo cp -r deploy/demo/legal /srv/inkling-demo/legal
# edit the four placeholders in /srv/inkling-demo/legal/*.md, then in demo.env:
#   DEMO_LEGAL_DIR=/srv/inkling-demo/legal
deploy/demo/demo.sh up

서버는 시작할 때 폴더를 한 번 읽습니다. signup.json 형식이 틀리면 로그에 파일 이름과 이유를 남기고 멈춥니다. 문서에 자리표시자가 남아 있으면 시작할 때마다 경고합니다. 폴더의 버전은 파일 내용의 해시라서, 파일을 고치고 다시 시작하면 운영자를 포함한 모든 계정이 다음 요청에서 다시 동의해야 합니다. 다시 시작하면 열려 있던 편집 연결도 끊기므로, 옛 약관으로 계속 쓰는 사람은 없습니다.

폴더에 들어가는 파일은 다음과 같습니다.

파일쓰임
terms.ko.md, terms.en.md이용약관. /terms에 보입니다
privacy.ko.md, privacy.en.md개인정보 처리방침. /privacy에 보입니다
signup.json가입 화면 맨 위 고지와 체크 항목(id, required, label, 선택 doc과 details)

한 언어로만 쓴 문서는 모든 사람에게 그 언어로 보입니다. 문서는 Markdown입니다. 문서 안의 HTML은 글자로 보이고, 링크는 http, https, mailto만 동작합니다.

틀은 이 문서의 설정으로 앱이 하는 일을 적었습니다. 설정을 바꾸면 그 설정에 관한 문장(가입 14일 뒤 삭제, 휴지통 7일, 한도, 꺼 둔 기능)을 확인합니다.

3. 프록시

PUBLIC_URL에 적은 주소로 127.0.0.1:3100 앞에 HTTPS를 둡니다. https 주소면 로그인 쿠키에 Secure가 붙습니다. 호스트에서 Caddy를 쓰면 다음과 같습니다.

demo.example.com {
	encode gzip zstd
	reverse_proxy 127.0.0.1:3100
	header {
		Strict-Transport-Security "max-age=31536000"
		X-Content-Type-Options "nosniff"
		Referrer-Policy "strict-origin-when-cross-origin"
	}
}

TRUST_PROXY=loopback,uniquelocal이면 프록시에서 온 요청은 X-Forwarded-For에서 실제 주소를 읽습니다. IP별 가입 횟수 제한에 이 주소가 필요합니다. 프록시가 접근 로그를 남긴다면 그 로그에도 IP 주소가 들어 있습니다. 처리방침 틀은 앱 자체의 기록(10MB 파일 세 개, 오래된 것부터 지움)을 적었으니, 프록시 로그도 그보다 오래 두지 않거나 그 규칙을 처리방침에 적습니다.

4. 설정 링크로 운영자 계정 만들기

deploy/demo/demo.sh logs app | grep -A2 'No accounts yet'

로그에 나온 /setup?code=… 링크를 엽니다. 링크는 PUBLIC_URL로 만들어지므로 프록시를 거쳐 공개 주소에서 열립니다. 서버는 PUBLIC_URL이 아닌 출처에서 보낸 양식을 거절하므로 그 주소를 씁니다(PUBLIC_URL을 그렇게 바꾸지 않았다면 터널로 연 localhost:3100에서는 안 됩니다). 링크는 계정이 하나도 없을 때 한 번만 쓸 수 있고, 그 전에 다시 시작하면 새 링크가 나옵니다. 설정 화면에도 가입 화면과 같은 동의 항목이 나옵니다. 운영자도 약관에 동의합니다. 관리자 계정은 만료되지 않습니다. 계정이 생기면 가입 화면이 모두에게 열립니다.

5. 알리기 전에 확인할 것

  • 시작 로그에 켜진 한도 한 줄, 꺼진 기능 한 줄, 버전이 적힌 LEGAL_DIR 한 줄이 있고, 자리표시자 경고는 없습니다.
  • curl -s https://demo.example.com/api/auth/mode에 loginId, instanceLabel, legal, limits(trashDays 포함), disabledFeatures가 보이고 setupPending이 false입니다.
  • 시크릿 창에서 가입 화면이 아이디를 묻고, 고지와 체크되지 않은 항목 여섯 개를 보여 주며, 모두 체크하기 전에는 가입 단추가 꺼져 있습니다. /terms와 /privacy는 로그인하지 않아도 열립니다.
  • 가입한 뒤 삭제 예정일이 보이고, 휴대폰과 컴퓨터 모두에서 "Demo" 표시가 보입니다.
  • deploy/demo/demo.sh config가 ok 줄만 보여 주고, deploy/demo/demo.sh ps에 공개된 데이터베이스 포트가 없으며 앱은 127.0.0.1:3100만 있습니다.
  • deploy/demo/demo.sh up이 ok DEMO_VOLUME_ROOT is a filesystem of its own을 보여 주었고, 그 폴더의 df -h가 0단계에서 정한 크기를 보여 줍니다.
  • 관리자 › 백업에 일 7, 주 0, 월 0이 보이고, 관리자 › 상태에 서버 저장 공간 상한이 보입니다.
  • 한 네트워크에서 하루에 세 번째 가입은 거절됩니다(프록시가 실제 주소를 넘깁니다).

운영자가 알아야 할 것

계정은 실제로 지워집니다

ACCOUNT_LIFETIME_DAYS=14는 가입 14일 뒤에 계정과 그 사람의 비공개 페이지와 파일, 그 사람만 있던 워크스페이스를 접속 여부와 상관없이 지웁니다. 백업에는 최대 7일 더 남습니다. 이 설정을 켜기 전에 만든 계정과 관리자 계정은 이 설정으로 지워지지 않습니다.

실제로 지우기 전에 무엇을 지울지 보려면 ACCOUNT_LIFETIME_DRY_RUN=1로 시작합니다. 그러면 매시간 도는 정리 작업이 지울 계정마다 로그 한 줄(계정 id와 함께 지워질 워크스페이스 수)을 남기고 아무것도 지우지 않습니다. 첫 계정들의 삭제 예정일이 지나고 로그에 정확히 그 계정들만 나오면, 값을 비우고 deploy/demo/demo.sh up을 다시 실행합니다.

디스크와 저장 공간 퓨즈

LIMIT_INSTANCE_STORAGE_MB=3000은 데이터베이스와 업로드(디스크에서 차지하는 블록)가 3,000 MB에 닿으면 쓰기를 멈춥니다. 그러면 데모는 읽기, 로그인, 내보내기, 삭제만 하고, 앱은 그렇다고 알리는 띠를 보여 줍니다. 행을 지워도 데이터베이스 파일은 줄지 않으므로, 대개 손으로 공간을 비울 때까지 그대로입니다. 할 일은 OPERATIONS.ko.md의 "인스턴스 저장 공간 퓨즈"에 있습니다. 주소 몇 개가 1~2분 동안 최대 속도로 쓰면 일부러 끊을 수도 있고, 그때 멈추는 것은 데모뿐입니다.

퓨즈는 WAL, 백업, 로그를 보지 못합니다. 이것들은 모두 데모의 파일시스템(0단계) 안에 있고, 크기도 이것들을 넣어 정합니다. 0.22.1에서 프로덕션 빌드로 재 보니 데이터베이스에 200 MB를 쓴 뒤 WAL이 약 880 MB였습니다.

워크스페이스 하나가 데이터베이스를 얼마나 키울 수 있는지도 0.22.1에서 쟀습니다. 워크스페이스의 저장 용량은 파일, 페이지 본문, 버전 기록, 검색 색인의 행을 세지만, Postgres의 색인 항목과 다시 쓸 때 남는 공간은 세지 않습니다. 10 MB 워크스페이스를 편집기의 실시간 연결이나 API로 글을 써서 한 번 가득 채우면 데이터베이스가 일반 문장으로는 9–19 MB, 일부러 쓴 무작위 단어로는 많아야 25.6 MB 늘었습니다. 그렇게 채운 워크스페이스 100개는 많아야 약 2.6 GB로 3,000 MB 퓨즈 아래입니다. 계정 몇 개가 지우고 다시 쓰기를 거듭하면 여전히 퓨즈를 일부러 끊을 수 있지만, 그때 멈추는 것은 데모뿐이고 파일시스템이 본 디스크를 지킵니다.

메모리

앱은 768 MB 컨테이너 안에서 448 MB 힙으로 돌고(NODE_OPTIONS, APP_MEM_LIMIT), 데이터베이스는 384 MB, 백업은 256 MB 안에서 돕니다. 셋 다 swap을 쓰지 않습니다(compose.demo.yaml에서 memswap_limit을 mem_limit과 같게 둠. 둘이 다르거나 한도가 빠지면 demo.sh가 거절합니다). 그래서 메모리가 모자란 컨테이너는 호스트의 swap으로 넘어가지 않고 멈췄다가 다시 시작합니다. 셋 다 코어 덤프를 남기지 않습니다(compose.demo.yaml의 ulimits: core: 0, demo.sh가 확인합니다). 호스트의 /proc/sys/kernel/core_pattern이 파이프(|…, systemd-coredump나 apport)이면 컨테이너 안에서 죽은 프로세스가 메모리째로 호스트의 처리기에 넘어가기 때문입니다. 데모를 열기 전에 서버에서 이 파일을 확인하세요.

0.22.1에서 프로덕션 빌드로 재 보니(macOS), 열려 있는 페이지는 저장 크기의 약 20배를 메모리에 둡니다. 계정 세 개가 두 워크스페이스 모두에서 가장 큰 페이지(2.5 MB, 워크스페이스 10 MB의 4분의 1)를 채우고 페이지를 모두 열어 두었을 때 힙 448 MB에서 힙이 최대 332 MB, 메모리가 최대 588 MB였습니다(워크스페이스마다 그런 페이지 하나 뒤로는 저장 한도가 거절함). 실시간 편집을 색인까지 쳐서 받기 전에는 같은 실행이 더 많이 채워져 힙 434 MB, 메모리 734 MB까지 갔고, 힙 320 MB와 384 MB에서는 메모리가 모자라 멈췄습니다. 힙을 올리면 APP_MEM_LIMIT도 같이 올리세요. 서버는 힙 말고도 255–325 MB를 썼습니다. 작은 map 항목이 아주 많은 페이지는 지금도 힙 448 MB를 넘길 수 있고(계정 하나, 페이지 두 개), 그러면 컨테이너가 다시 시작합니다.

공지 올리기

데모는 메일을 보내지 않고, 약관 틀은 공지(약관 변경, 서비스 변경, 중단, 개인정보 유출)를 앱 안과 로그인 화면에 올린다고 적었습니다. 그 수단이 INSTANCE_NOTICE입니다. demo.env에 적고(큰따옴표 안에서 \n이 줄바꿈, 500자까지) deploy/demo/demo.sh up을 다시 실행합니다. 내릴 때도 값을 비우고 같은 방법으로 합니다. 공지는 링크 없이 글자로만 보이고 닫을 수 없습니다. 다시 시작하면 열려 있던 편집 연결이 끊겼다가 바로 다시 붙습니다.

예고 없이 데모를 닫을 때

데모를 닫으면 데이터베이스, 파일, 백업을 지체 없이 지운다고 처리방침 틀에 적혀 있습니다.

deploy/demo/demo.sh destroy    # asks you to type inkling-demo

destroy는 up과 같은 검사를 거친 뒤 데모를 멈추고 볼륨과 이미지를 지운 다음, 파일이 아직 어디에 있는지 알려 줍니다. 볼륨은 DEMO_VOLUME_ROOT 아래의 폴더이고, 스크립트는 호스트의 파일을 지우지 않습니다. 폴더 네 개는 경로를 확인한 뒤 root로 직접 지우거나, 0단계의 파일시스템을 마운트 해제하고 그 이미지 파일을 지웁니다. 운영 인스턴스는 건드리지 않습니다. BACKUP_RCLONE_REMOTE를 썼다면 원격 백업 사본도, 데모 주소의 프록시 접근 로그도, 채운 약관 폴더와 demo.env도 지웁니다. 서버가 갑자기 멈췄다면 다시 접속할 수 있게 되는 대로 이 일을 합니다.

0.22.0 데모 옮기기

0.22.0으로 띄운 데모는 볼륨이 Docker 디스크의 이름 있는 볼륨이고, 운영의 이미지 이름을 쓰며, 0.22.0 기본값(워크스페이스당 20 MB, 512 MB 안의 320 MB 힙)입니다. 스스로 옮겨지지 않고, 데이터도 넘어가지 않습니다(docs/adr/2546-*).

  1. 데모를 언제 비우는지 INSTANCE_NOTICE로 알려서, 사용자가 남길 것을 내보낼 수 있게 합니다.
  2. 데모의 0.22.0 체크아웃에서 deploy/demo/demo.sh destroy를 실행합니다(데모의 컨테이너, 볼륨, 데이터를 지우고 운영 인스턴스는 건드리지 않습니다). 체크아웃을 올리기 전에 합니다. 0.22.1의 스크립트는 새 설정을 기대합니다.
  3. 0단계의 파일시스템을 만들고, 체크아웃을 0.22.1로 올리고, 새 demo.env.example에서 demo.env를 다시 채웁니다(DEMO_IMAGE, DEMO_VOLUME_ROOT, LIMIT_WORKSPACE_STORAGE_MB=10, APP_MEM_LIMIT=768m, NODE_OPTIONS=--max-old-space-size=448). 비밀 값은 새로 만든 것을 씁니다.
  4. 0.22.1 틀로 약관 폴더를 다시 채운 뒤(저장 용량 문장이 바뀌었습니다) 1단계부터 5단계까지 따릅니다. 운영자 계정은 설정 링크로 다시 만듭니다.

이 파일들은 법률 자문이 아닙니다

deploy/demo/legal/의 틀과 이 문서는 한 운영자의 데모를 위해 쓴 출발점이고, 법률 자문이 아닙니다. 읽어 보고 자기 사정과 나라에 맞게 고치고, 확실하지 않으면 확인을 받으세요. 틀에서 앱 동작을 설명하는 문장은 위 설정을 기준으로 썼습니다. 설정을 바꾸면 문장도 고쳐야 할 수 있습니다.
