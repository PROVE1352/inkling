Inkling API 계약 (M1)

웹 앱, 스크립트, MCP 도구가 함께 쓰는 REST 계약.

이 문서는 저장소의 docs/API.ko.md을 그대로 옮겼습니다. Markdown 원문

서버 에이전트와 웹 에이전트가 함께 따르는 계약입니다. 이 문서가 기준입니다. 구현은 이 문서와 달라지면 안 됩니다. 요청 검증 스키마와 DTO 타입은 @inkling/shared(packages/shared/src/index.ts)에 정의되어 있고, 서버와 웹 모두 이것을 가져다 씁니다. English: API.md.

공통 규칙

  • 모든 REST 엔드포인트는 /api 접두사를 쓰고 JSON으로 주고받습니다. 예외는 GET /files/:id(바이너리)와 WS /collab(Hocuspocus)입니다.
  • 인증: 세션 쿠키 inkling_sid(httpOnly, SameSite=Lax, Path=/, 30일, COOKIE_SECURE=1이면 Secure). 서버는 토큰의 SHA-256만 저장합니다(docs/adr/1060-*).
  • 교차 사이트 검사: Authorization 헤더가 없는 GET/HEAD/OPTIONS 외의 /api 요청에서 Origin(없으면 Referer)이 PUBLIC_URL/APP_URL이 아니면 → 403 CROSS_SITE_REQUEST. 두 헤더를 모두 보내지 않는 클라이언트(CLI, curl)는 허용합니다. /collab WebSocket 업그레이드도 같은 방식으로 검사합니다(docs/adr/1062-*).
  • 오류 응답 형식: { "error": { "code": string, "message": string } } (ApiErrorBody).
    • 코드: UNAUTHORIZED(401), FORBIDDEN(403), NOT_FOUND(404), VALIDATION(400), EMAIL_TAKEN(409), INVALID_CREDENTIALS(401), INVALID_CODE(404), INVALID_RESET(400), EMAIL_NOT_VERIFIED(403), DELEGATED_ACCOUNT(400), RATE_LIMITED(429, Retry-After), MAIL_DISABLED(501), MAIL_FAILED(502), CROSS_SITE_REQUEST(403), INVALID_TOTP_CODE(401), TOTP_CODE_REUSED(401), TOTP_CHALLENGE_EXPIRED(401), TWO_FACTOR_ALREADY_ON(409), TWO_FACTOR_UNAVAILABLE(501), PAYLOAD_TOO_LARGE(413), UNSUPPORTED_TYPE(415), INTERNAL(500).
    • message는 영어입니다. 클라이언트는 code를 보고 현지화합니다. 웹 앱은 알고 있는 코드를 번역하고(정확히 일치하는 일부 메시지도 번역합니다), 그 밖에는 message를 그대로 보여 줍니다. 메시지 문구로 판별하지 마세요.
  • 권한 모델: 워크스페이스의 모든 작업은 멤버만 할 수 있습니다. 페이지와 파일의 권한은 그것이 속한 워크스페이스로 확인합니다.

현지화

  • 지원 로케일: en, ko. 운영자가 DEFAULT_LOCALE(en | ko)을 정할 수 있습니다(정하지 않으면 서버는 en을 씁니다).
  • 웹 클라이언트는 모든 API 요청에 Accept-Language: <ui locale>을 보냅니다.
  • 서버가 만드는 내용(기본 제공 템플릿, Tasks 문서처럼 서버가 만드는 페이지의 기본 제목, 컬렉션의 기본 속성과 뷰, 가입할 때 만드는 워크스페이스 이름)은 사용자가 저장한 로케일을 쓰고, 없으면 Accept-Language, 그것도 없으면 DEFAULT_LOCALE을 씁니다.
  • 이메일은 받는 사람이 저장한 로케일을 쓰고, 없으면 DEFAULT_LOCALE을 씁니다.
  • 오류 message는 현지화하지 않습니다(공통 규칙 참고).
  • 관련 엔드포인트: GET /api/auth/mode(defaultLocale), GET /api/auth/me(user.locale), PATCH /api/auth/me/locale(인증 참고).

공개 폴더 공유 (2026-09-23)

폴더(kind='folder')를 공개 링크 하나로 공유합니다. 링크를 가진 사람은 로그인하지 않고도 폴더의 현재 하위 트리를 둘러보고 읽을 수 있습니다. 게시와 중지 규칙은 페이지 하나를 공유할 때와 같습니다(워크스페이스 소유자만, scope='private' → 400). 기존 단일 페이지 공유 동작은 바뀌지 않습니다.

  • 하위 트리 = 요청할 때 계산합니다(재귀 CTE). 나중에 추가되거나 옮겨 들어온 페이지는 저절로 들어가고, 밖으로 옮겨진 페이지는 저절로 빠집니다. 휴지통에 있는 페이지(deleted_at), 개인 페이지(scope='private'), 템플릿 페이지에서는 더 내려가지 않습니다 → 그 하위 트리 전체가 빠집니다. 같은 워크스페이스 안에서만이고, 깊이 제한은 64입니다.
  • ref(불투명 식별자): ref = base64url(HMAC-SHA256(key=shareToken, msg=pageId))의 앞 22자. 내부 페이지 UUID는 공개 응답이나 URL에 절대 나오지 않습니다(M15 유출 금지 원칙). 단방향이라 ref에서 pageId를 거꾸로 알아낼 수 없습니다. 공유를 멈췄다가 다시 하면 토큰이 바뀌므로 모든 ref도 바뀝니다. 서버는 요청마다 하위 트리를 다시 계산해 ref를 찾습니다(매핑 테이블 없음, 마이그레이션 없음).
  • 하위 트리 밖 / 휴지통 / 개인 / 없음 / 볼 수 없는 종류 → 언제나 404(403이 아님).

수정 단계 변경 사항 (docs/adr/0800–0815)

오류에 필드가 더 붙을 수 있습니다. AppError.details는 error 객체에 합쳐집니다. { "error": { "code": "...", "message": "...", ...details } }. 클라이언트는 모르는 키를 무시해야 합니다.

DELETE /api/admin/users/:id: 409 SOLE_OWNER. 그 사용자가 어느 워크스페이스든 유일한 소유자이면 거절합니다.

{ "error": { "code": "SOLE_OWNER", "message": "…", "workspaces": [{ "id": "uuid", "name": "Team" }] } }

관리자 UI는 workspaces를 보여 주고 먼저 다른 멤버를 소유자로 올리라고 안내해야 합니다 (그 워크스페이스의 소유자가, 또는 그곳의 멤버/소유자인 관리자가 PATCH /api/workspaces/:id/members/:userId { role: "owner" }를 호출합니다). 삭제에 성공하면 그 사용자의 개인 페이지는 작성자 없이 휴지통으로 갑니다. 아무도(관리자 포함) 그 페이지를 보거나 복원하거나 영구 삭제할 수 없고, 30일 휴지통 정리가 지웁니다.

보이기 규칙. 작성자가 더는 없는 개인 페이지(created_by IS NULL)는 아무에게도 보이지 않습니다. 이런 페이지가 들어 있는 공유 하위 트리를 개인 섹션으로 옮기면, 옮긴 사람이 그 페이지들의 작성자가 됩니다.

페이지 트리 변경 (parentId를 준 POST /pages, parentId/scope를 준 PATCH /pages/:id, 복원/영구 삭제, 복제/캔버스 펼치기, POST /pages/from-template, 볼트 동기화의 생성, 가져오기, 컬렉션 행 일괄 처리):

  • 400 VALIDATION: 부모가 없거나, 휴지통에 있거나, 다른 워크스페이스에 있을 때, 순환이 생길 때, 결과가 64단계보다 깊어질 때.
  • 403 FORBIDDEN: 부모가 공개 링크가 걸린 폴더/페이지 안에 있고 호출한 사람이 워크스페이스 소유자가 아닐 때(같은 공개 폴더 안에서 옮기는 것과 공개된 컬렉션에 새 행을 넣는 것은 계속 허용됩니다).

GET /api/workspaces, POST /api/workspaces/join: 호출한 사람이 그 워크스페이스의 소유자가 아니면 inviteCode는 ""입니다. 소유자가 다른 사람을 내보내는 DELETE /api/workspaces/:id/members/:userId 호출은 초대 코드를 새로 만듭니다.

PATCH /pages/:id/props, 컬렉션 행 일괄 처리: 사람 칸이 워크스페이스 멤버가 아닌 사용자를 가리키면 400입니다.

POST /pages/:id/publish/notion: 실제 업로드(dry-run이 아닌 것)는 소유자만 할 수 있고(403), 분당 10회로 제한됩니다.

템플릿: 개인 페이지에서 저장한 템플릿(또는 private: true로 저장한 템플릿)은 만든 사람에게만 목록에 나오고 쓸 수 있습니다. DELETE /templates/:id는 만든 사람이나 워크스페이스 소유자만 할 수 있습니다. 템플릿을 보세요.

가져오기: 폴더 깊이 ≤ 32, 만들어지는 페이지는 많아야 IMPORT_MAX_PAGES(기본 5000)개, zip 항목은 실제로 푼 바이트로 잽니다(항목 하나당 IMPORT_MAX_ENTRY_MB, 기본 25. 전체 IMPORT_MAX_UNPACKED_MB, 기본 50). 파일은 많아야 IMPORT_MAX_FILES(기본 300)개입니다. 넘으면 → 400. 가져온 첨부 파일의 pageId는 그 파일을 처음 참조하는 페이지입니다.

로그인: 로그인을 확인하는 사이에 비밀번호 재설정이 커밋되면 401(비밀번호가 방금 바뀜)입니다. 비밀번호를 재설정하면 iCal 피드 토큰도 폐기됩니다.

GET /api/health/ready: 200 {ok:true, db:true} / 503 {ok:false, db:false}(DB select 1, 2 s 타임아웃, 5 s 캐시). /api/health는 그대로 생존 확인(liveness)입니다.

협업: 서버 종료 중이거나 DB가 실패한 동안의 업그레이드는 503을 받습니다. 접근 권한이 빠지면 서버가 Hocuspocus PermissionDenied 메시지를 이유 permission-changed와 함께 보낸 뒤 코드 4403으로 소켓을 닫습니다.

정적 파일: 없는 /assets/* 파일은 404입니다(SPA 셸을 주지 않습니다).

데이터베이스(컬렉션) (docs/adr/2140–2147, 2192)

  • 속성 타입 email, phone, createdTime, editedTime, createdBy, editedBy, uniqueId({ uniqueId: { prefix } })가 생깁니다. relation.subItems: true는 컬렉션이 자기 자신을 가리키는 상위 항목(Parent item) 관계임을 표시합니다. ID와 상위 항목은 컬렉션마다 하나씩만 둘 수 있습니다(400). PUT /pages/:id/collection/fields가 이것들을 검증합니다.
  • GET /pages/:id/collection(과 다른 행 응답): 행의 props에 자동 값이 들어갑니다(createdTime / editedTime은 ISO UTC 문자열, createdBy / editedBy는 사용자 id이고 에이전트가 바꿨을 때는 via:<fieldId>에 클라이언트 이름이 들어가며, uniqueId는 숫자). 페이지 게스트도 부를 수 있고(공유받은 트리 밖은 404), 게스트의 응답에는 people: { [userId]: name }이 더해집니다.
  • 페이지 게스트에게 열린 경로(쓰기는 편집 권한이 있어야 함): GET /pages/:id/collection/row-options, GET …/covers, GET …/row-templates, POST …/collection/rows, PATCH /pages/:id/props. 게스트가 person 값을 넣으면 403 GUEST_PERSON입니다. 속성, 뷰, 일괄 붙여넣기와 가져오기, 차트, 멤버 목록은 그대로 멤버만 씁니다.

  • GET /pages/:id/collection/query: under(행 id, TASK-3 같은 ID, 또는 정확한 제목)와 depth(1–8, 기본값 1)가 생깁니다. 필드 요약에 prefix(uniqueId)와 subItems: true가 붙습니다. 자동 값은 필터나 정렬이 가리키는 필드만 SQL로 계산하고, 돌려주는 행의 자동 값은 그 행들을 한 번 더 읽어서 채웁니다(ADR 2192). 응답 모양은 그대로입니다.

가입 (docs/adr/2501, 2512, 2516, 2519)

  • POST /api/auth/register는 새 선택 필드를 받습니다. LEGAL_DIR이 있으면 consents: string[](체크한 항목 id, 32개까지)와 legalVersion(양식이 보여 준 버전), signupChecks가 켜져 있으면 website(비워 둬야 하는 숨은 입력란)와 formMs(양식이 화면에 떠 있던 밀리초, 2000 이상)입니다. formMs는 보낸 본문에서 그대로 읽고 registerSchema에는 없습니다.
  • LOGIN_ID_MODE=username이면 본문에 email 대신 loginId를 보냅니다. email을 보내면 400 VALIDATION, 아이디가 없거나 규칙에 맞지 않으면 400 LOGIN_ID_INVALID, 이미 쓰이면 409 LOGIN_ID_TAKEN입니다. 아이디는 소문자로 바꿔 계정의 이메일 열에 저장하므로 UserDTO.email에 아이디가 들어갑니다. 로그인은 지금처럼 email에 아이디를 넣어 보냅니다. 이메일 모드에서는 loginId 필드를 무시합니다.
  • 검사 순서: 본문, 예약된 위임 도메인, 설정 코드, 그다음 제한 모드 검사(봇 검사, 계정 수 상한, 주소별 상한, 동의)입니다. 모두 가입 키를 쓰거나 무엇을 쓰기 전에 합니다. 계정 수 상한과 주소별 상한은 계정을 만드는 트랜잭션 안에서 다시 세고, 동의 행도 거기서 씁니다. 설정 코드로 만드는 첫 관리자는 계정 수·주소별 상한과 봇 검사를 거치지 않지만 동의는 해야 합니다.

  • 감사 이벤트(GET /api/workspaces/:id/audit): page.locked와 page.lock_editors_changed는 이제 editors 옆에 editorIds를, agent.blocked와 agent.unblocked는 user 옆에 userId를 저장해서 계정 삭제가 이름을 id로 찾을 수 있습니다. 감사 라우트는 before와 after에서 이 id 키를 빼고 돌려줍니다.
  • DELETE /api/workspaces/:id/members/:userId를 자기 자신에게, 유일한 멤버이자 마지막 소유자로서, 워크스페이스 이름과 같은 { name } 본문을 실어 브라우저 세션에서 보내면 204이고 워크스페이스를 파일까지 바로 지웁니다(복원 없음). 이름이 틀리면 400이고, name이 없거나 토큰으로 보냈거나 다른 멤버가 있으면 지금처럼 400입니다.
  • DELETE /api/workspaces/:id/permanent 본문 { name } → 204. 소유자가 삭제된(아직 복원할 수 있는) 워크스페이스를 바로 완전히 지웁니다. 브라우저 세션에서만 되고(bearer 토큰은 403), 삭제되지 않았거나 없거나 멤버가 아니면 404, 소유자가 아니면 403, 워크스페이스의 2단계 인증 규칙은 복원과 같이 적용되고, 이름이 틀리면 400입니다.

사용량과 한도 (docs/adr/2505–2506)

  • GET /api/workspaces/:id/usage(멤버) → WorkspaceUsageDTO { members, pages, storageBytes, fileBytes, limits: { members?, pages?, storageBytes? } }. pages는 휴지통도 세고, storageBytes는 저장 용량 합계(파일 포함), fileBytes는 파일만입니다. limits에는 설정된 한도만 들어가고 저장 용량은 바이트입니다. 모든 서버에서 캐시한 값으로 답하고, 그 값이 1분보다 오래되었으면 먼저 다시 셉니다(그래서 한도가 있든 없든 워크스페이스마다 1분에 한 번까지).
  • 한도를 넘는 생성은 만드는 트랜잭션 안에서 거절합니다. REST도, 그 REST를 부르는 MCP 도구도 같습니다. 페이지(만들기, 복제, 캔버스, 행과 행 일괄, 가져오기, 템플릿, 나누기, 클립, 빠른 할 일, 동기화, 폼 응답), 파일, 워크스페이스(만들기, 넘겨받기, 소유자로 승격, 복원), 멤버(초대 코드로 참여, 바로 추가)가 그렇습니다. 이미 멤버인 워크스페이스에 다시 참여하면 다시 세지 않습니다.
  • LIMIT_WORKSPACE_STORAGE_MB에 닿은(사용량 ≥ 한도) 워크스페이스는 읽기 전용입니다. 담긴 것을 키울 수 있는 쓰기는 모두 413 LIMIT_STORAGE로 답하고, 협업 연결은 읽기 전용 범위를 받습니다. POST, PUT, PATCH 라우트는 모두 apps/server/src/quota/writeSweep.test.ts에 검사함 또는 열어 둠(이유와 함께)으로 적혀 있습니다(docs/adr/2533-*). 거절하는 것: 페이지 만들기(복제, 캔버스 펼치기, 섹션, 나누기와 순환 대상, 템플릿에서 만들기, 온보딩 예시 포함), 본문 쓰기(/content, /section, /ink, 동기화 Markdown, 페이지·변경·워크스페이스 되돌리기), 버전(POST /snapshots, 버전 복원), 행(만들기, 일괄 만들기와 바꾸기, 폼 응답), PATCH /pages/:id/props, 컬렉션 필드, 뷰와 행 템플릿 새로 만들기와 바꾸기, 제목·아이콘·표지·별칭·날짜 속성을 바꾸는 PATCH /pages/:id, 새 댓글과 댓글 본문 고치기, 제안 수락과 모든 새 제안, 업로드, 클립, 빠른 할 일, vault 동기화 페이지, 가져오기와 폴더 가져오기, 템플릿, 시트 동기화 실행, 새 자동화· 웹훅·공유 링크. 열어 두는 것: 없애기, 게시 취소, 거절, 휴지통이나 삭제에서 복원, 멤버와 역할(참여는 LIMIT_MEMBERS를 그대로 받음), 그 자리에서 바꾸는 크기가 정해진 설정(워크스페이스 이름과 설정, 에이전트 정책과 규칙, 잠금, 소유자, 페이지 접근, 공유 링크의 만료와 비밀번호, 자동화 규칙, 검증과 검토), 할 일 체크나 날짜 옮기기, POST로 보내는 읽기, 그 사람에 관한 것, 관리자 라우트, POST /mcp(그 도구는 위의 라우트를 부름).
  • 이 검사는 캐시한 값을 요청 JSON 크기만큼 바로 올립니다(다음 계산 전까지의 위쪽 어림값). 캐시한 값으로는 들어가지 않는데 최근 10초 안에 센 적이 없으면 답하기 전에 워크스페이스를 다시 셉니다. 그래서 한도 가까이의 큰 쓰기는 잠깐 거절될 수 있습니다. 본문이 한도의 1/4을 넘은 페이지는 REST와 MCP 쓰기를 413 LIMIT_STORAGE로 거절합니다("This page is too large to grow further: move part of it to a new page", limit은 그 1/4).

  • 내장 상한(브라우저 25 MB, 토큰은 AGENT_UPLOAD_MAX_MB)보다 작은 LIMIT_FILE_MB가 있으면 POST /api/files는 413 LIMIT_FILE로 답합니다. 없으면 지금처럼 413 PAYLOAD_TOO_LARGE입니다.
  • LIMIT_WORKSPACES_TOTAL(docs/adr/2531-*): 서버의 워크스페이스 수(삭제했지만 아직 복원할 수 있는 것 포함)를 넘는 POST /api/workspaces는 { limit, used }가 붙은 403 LIMIT_WORKSPACES_TOTAL로 답합니다. 가입과 새 OIDC 계정은 대신 SIGNUP_FULL을 받습니다.
  • LIMIT_INSTANCE_STORAGE_MB(docs/adr/2532-*): 퓨즈가 끊긴 동안 /api 아래의 POST, PUT, PATCH는 인증보다 먼저 503 INSTANCE_FULL로 답합니다. 예외는 OPEN_WHEN_FULL의 라우트(apps/server/src/quota/instanceGate.ts: 로그인과 로그아웃, 비밀번호 바꾸기와 재설정, 2단계 인증 설정, 동의, POST로 보내는 읽기, 읽음 표시, 없애거나 넘기기만 하는 라우트)와 /api/admin/**입니다. GET과 DELETE는 언제나 통과합니다. POST /oauth/register는 OAuth 오류 형식의 503 temporarily_unavailable로 답합니다.

기능 끄기 (docs/adr/2507)

  • POST /oauth/register는 두 경우에 503 temporarily_unavailable로 답합니다. 인스턴스 저장 공간 퓨즈가 끊겼을 때(먼저 확인합니다), 그리고 OAUTH_UNUSED_CLIENT_MAX에 닿았는데 쓰이지 않은 클라이언트가 모두 15분이 안 되었을 때입니다 (Retry-After: 60과 함께). 상한이 있으면 등록은 먼저 가장 오래된, 쓰이지 않은 클라이언트를 지웁니다.
  • OAUTH_UNUSED_CLIENT_HOURS나 OAUTH_UNUSED_CLIENT_MAX로 지워진 자체 등록 클라이언트는 모르는 클라이언트가 됩니다. 인가 단계가 400 INVALID_CLIENT("Unknown app. Connect again from the app.")로 답하고, 앱은 다시 등록해야 합니다 (docs/adr/2536-*). 아무것도 가리키지 않는 클라이언트만 지우므로, 코드나 grant가 있는 클라이언트는 이런 일을 겪지 않습니다.
  • 모든 서버에서 grant_type=authorization_code인 POST /oauth/token은 코드를 쓰는 일과 grant를 저장하는 일을 한 트랜잭션으로 합니다. 응답은 그대로입니다.

LIMIT_FILE_MB가 AGENT_UPLOAD_MAX_MB보다 작으면 upload_file의 설명에 작은 쪽 크기가 적힙니다. 도구는 자기가 부르는 REST 라우트를 거치므로 같은 한도, 기능 끄기, 동의에 똑같이 걸리고, 이 코드들의 오류에는 각자의 다음 할 일 안내가 붙습니다(INSTANCE_FULL도 그렇습니다. 아무것도 쓰지 않았고, 다시 시도하지 말고, 운영자가 공간을 비워야 한다고 알립니다). list_trash의 날짜는 LIMIT_TRASH_DAYS를 따릅니다. 자세한 내용: MCP.ko.md.

v0.22.1 변경 사항

추가하거나 없앤 라우트도, 마이그레이션도 없습니다(docs/adr/2540-* .. 2551-*). 클라이언트나 연동이 알아챌 수 있는 것은 다음과 같습니다.

  • 사용량(GET /api/workspaces/:id/usage): LIMIT_WORKSPACE_STORAGE_MB가 있으면 storageBytes는 검색·섹션 색인의 행도 세고, 파일 하나를 max(size, 4,096) + 1,024바이트로 셉니다(fileBytes도). 이 값은 캐시해 둔 수치라서, 아직 재계산이 보지 못한 저장의 추정값이 들어 있을 수 있습니다. 본문이 늘어난 바이트마다 색인 행 몫으로 2바이트이고, 색인 패스 뒤의 재계산까지 남습니다(docs/adr/2545-, 2548-). 이 설정이 없으면 둘 다 0.22.0처럼 셉니다.
  • **페이지 손님에게 가는 413 LIMIT_STORAGE*에는 코드와 메시지만 있고 limit, used, unit은 없습니다 (docs/adr/2547-). 멤버는 여전히 받습니다. 협업 소켓은 이 숫자를 보내지 않습니다.
  • **PATCH /api/pages/:id*는 저장 한도가 있을 때 멤버십과 편집 권한을 저장 용량보다 먼저 확인합니다. 페이지를 읽기만 할 수 있는 사람은 413이 아니라 편집 검사의 403을 받습니다(docs/adr/2547-).
  • 감사 이벤트: page.access_granted, page.access_changed, page.access_removed와 페이지 초대 수락의 접근 부여는 person 옆에 personId를 남깁니다. GET /api/workspaces/:id/audit은 다른 id 키처럼 personId를 빼고 보여 줍니다. 본인이나 만료로 계정을 삭제하면 personId가 그 계정 id인 곳의 person과 personId를 null로 바꾸고, 계정 자신의 로그인 이메일이나 아이디를 주소로 적은 page.guest_invited 행의 email을 null로 바꿉니다.
  • 협업 소켓, 저장 용량(LIMIT_WORKSPACE_STORAGE_MB나 LIMIT_INSTANCE_STORAGE_MB가 있을 때만):
    • 들어가지 않는 갱신은 적용하지 않습니다. 연결은 읽기 전용이 되고, 상태 메시지 {"t":"storage","why":W}를 받고, 닫힘 코드 4000 storage-full로 닫힙니다. W는 "workspace"(워크스페이스의 자리), "page"(페이지 본문의 상한), "structs"(새 값: 페이지가 Yjs 구조 300,000개를 넘게 됨, docs/adr/2540-*), "instance"(퓨즈)입니다. 프로바이더는 다시 붙어 읽기 전용 범위를 받습니다. "workspace"나 "page" 뒤에는 그 페이지가 10분 동안 또는 재계산이 자리를 찾을 때까지, "structs" 뒤에는 10분 동안, "instance" 뒤에는 퓨즈가 끊긴 동안 읽기 전용으로 열립니다.
    • 저장이나 재계산으로 워크스페이스가 한도를 넘거나 페이지 본문이 상한을 넘으면, 모든 편집 연결이 {"t":"storage","why":"workspace"}나 {"t":"storage","why":"page"}를 받고 같은 닫힘 4000 storage-full로 닫힙니다 (0.22.1 전: 닫힘 4403 permission-changed, 그 뒤 웹 앱이 다시 붙지 않았음). 재계산이 자리를 찾으면 읽기 전용 연결을 4000으로 닫고, 연결은 읽기·쓰기 범위로 돌아옵니다. 4403은 접근이 바뀐 경우에만 씁니다.
    • 갱신은 센 값 + 3 × (저장 안 된 증가분 + 이 갱신) + 다음 버전 사본이 들어갈 때 받아들입니다. 저장 안 된 증가분은 문서가 실제로 받아들인 만큼이라서, 문서가 이미 가진 갱신을 다시 보내도 늘지 않습니다(docs/adr/2543-, 2548-).
  • 협업 소켓, 모든 서버(docs/adr/2541-, 2542-, 2544-*). 클라이언트를 만드는 사람이 알아야 할 것입니다.
    • 수신함 문서(inbox:<userId>)는 읽기 전용으로 인증됩니다. 구조나 삭제가 든 Sync 갱신이나 sync step 2를 보내면 거절하고 소켓을 끊습니다. 빈 step 2만 통과합니다. 서버가 이 문서로 보내는 상태 메시지 알림은 그대로입니다.
    • awareness: 문서 연결 하나가 문서에 새로 들여올 수 있는 클라이언트 id는 4개까지입니다(문서에 그 id의 상태가 없을 때 그 id를 더한 메시지의 연결이 셉니다. Hocuspocus 프로바이더처럼 다른 클라이언트의 상태를 되돌려 보내는 것은 세지 않습니다). 소켓 하나는 새 클라이언트 id를 한 번에 64개, 그 뒤로는 1초에 하나씩 더할 수 있고, 문서 하나는 id를 1024개까지, 상태 하나는 16 KB, 메시지 하나는 1 MB, 소켓의 연결들이 들여온 상태는 합쳐서 256 KB까지이고, 소켓 하나가 바꾸는 상태는 한 번에 128 KB, 그 뒤로 1초에 16 KB까지입니다(아무것도 바꾸지 않는 항목은 세지 않습니다). 두 속도 상한(새 id, 바꾸는 상태) 가운데 하나를 넘는 메시지는 버립니다. 적용하지 않고 다른 연결에 보내지도 않으며 소켓은 그대로 두고, 다음에 오는 상태가 그 자리를 대신합니다. 그 밖의 상한을 하나라도 넘는 메시지는 적용하지 않고 소켓을 끊습니다. 닫힌 연결이 들여온 id는 지웁니다.
    • 끊는 소켓은 닫힘 프레임 없이 끝냅니다(브라우저는 1006으로 보고합니다). 프로바이더는 다시 붙습니다.
    • 클라이언트 주소마다 소켓은 40개까지이고(코드의 상수, collab.ts의 MAX_CONN_PER_IP), IPv6 /64는 주소 하나로 셉니다. 넘으면 업그레이드 요청에 429로 답합니다.
  • replace(POST /api/pages/:id/content의 replace, update_page와 patch_section의 replace, patch_sections, 되돌리기. 모든 서버, docs/adr/2550-*): 범위의 옛 블록과 새 블록의 글자가 합쳐 128 KiB를 넘으면 편집에 예산이 붙습니다 (Yjs 텍스트 연산 2,000번, diff 4천만(40 million) 단계). 예산을 넘으면 바뀐 블록은 id, 색, 정렬, 토글을 지키고 내용만 통째로 바뀝니다. 응답은 그대로입니다. 128 KiB 이하의 범위는 전과 똑같이 편집합니다.
  • AI 단계(GET /api/pages/:id/snapshots의 step): 에이전트의 update_page replace는 새 본문이 2,000블록을 넘거나 마크다운이 262,144자를 넘으면 added와 removed가 없습니다. 원래 페이지가 2,000블록을 넘었을 때와 같습니다 (docs/adr/2551-*).
