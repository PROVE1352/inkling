Performance log

Every performance change with numbers before and after, and how they were measured.

Rendered from docs/PERFORMANCE.md in the repository. Markdown source

This file records every algorithm or data-structure change made for performance, with the numbers before and after and how they were measured. It also records changes that were measured and rejected, changes that had no effect, and regressions, so the same idea is not tried twice and a slowdown is never silent. The reasoning behind each change lives in its ADR (docs/adr/); this file is the index of the numbers. 한국어: PERFORMANCE.ko.md.

Measurement principles

  • Same data, same conditions. Before and after run on the same seed, machine and settings, ideally back to back or interleaved. A number measured on different data is not a comparison.
  • Distributions, not single runs. Report p50 and p95 (or median and range) for latency, and the number of runs. Ranges in the tables are the spread over runs as given in the ADR.
  • State the load. Concurrency (sequential, N parallel clients), data size (pages, rows, chunks, blocks, bytes) and whether caches were warm.
  • State the environment. Node version, Postgres version, browser engine and build type (production or dev server), machine class and database size.
  • Link the source. Every number links to the ADR (and, where possible, the commit) where it was recorded together with its script or test. A number without a source does not go in.
  • Improvement is computed from the Before and After cells of the same row: percentages for token and size reductions, multiples (×) for time. Ranges in the inputs give a range here; no midpoint is picked.
  • Cost lists what the change made worse or what it trades away. An honest cost is not a regression; a regression is a measured slowdown of something users already had.

The entries below were recorded before this log existed. Their "How measured" cell repeats only what the ADR states; Node version, hardware and run counts are given where the ADR records them and are otherwise not recorded. Commit hashes are not listed yet; the ADR is the source.

ADR 2545

Restricted mode (0.22, not measured; a description of the structure from the code). With a limit set, every transaction that creates pages takes a transaction-scoped advisory lock per workspace (ws-quota:<workspace>) and counts the workspace's pages rows under it; adding a member counts workspace_members under the member lock; creating or taking over a workspace counts the person's owned workspaces under user-ws:<user>. With LIMIT_WORKSPACE_STORAGE_MB an upload reads and updates the workspace's cached count in its transaction, each save of a page body runs one UPDATE … RETURNING on the workspace row, a REST or MCP body write reads the workspace row and the page's stored body size, and a full count (one statement over about a dozen tables of the workspace) runs every hour for every workspace in turn, at a save when the cached count is more than 10 minutes old, when Workspace settings › General finds it more than a minute old, and after a purge. With LEGAL_DIR each authenticated request asks whether the person agreed: "agreed" is cached for 10 minutes (at most 20,000 entries), "not agreed" is read from user_consents each time. With none of the settings the checks return before any SQL (a test passes them an executor that throws), and a request costs one length check for the features turned off and one size check for the request gates. Two things run without any setting: GET /api/workspaces/:id/usage, which Workspace settings › General calls on every server, runs the full count when the workspace's cached count is more than a minute old (so at most once a minute per workspace) and stores it, and the hourly housekeeping runs two more DELETE statements (old sign-up records and old ip_bans rows). LIMIT_TRASH_DAYS changes only the interval inside the existing trash purge statement (LEAST(trash_retention_days, cap)); without it the statement is the 0.21.1 one. With LIMIT_WORKSPACE_STORAGE_MB or LIMIT_INSTANCE_STORAGE_MB (docs/adr/2530-* .. 2533-*), every live-editing update is counted before it is applied against sums in memory and a byte budget per client address (no SQL on that path; the cached count is re-read in the background when older than 2 s), the writes that can grow a workspace run one UPDATE adding the request's JSON size, and the fuse runs at most once a minute one pg_database_size query and a walk over every file of the data folder. The only numbers are ADR 2530's, from the development server (tsx), not a production build: 40 pages × 8 MB on one socket stored 18.0 MB under a 20 MB limit with resident memory 356 → 615 MB at the peak, against 320 MB stored and 2.1 GB before the fix.

How to add an entry

  • A pull request that changes an algorithm or data structure for performance must add a row to the matching table above, with before and after numbers and how they were measured. A change that was measured and not kept goes under "Rejected / no effect"; a measured slowdown goes under "Regressions".
  • Measure before and after on the same data and machine, following the principles at the top. Record data size, concurrency, p50/p95 (or median and range), run count, Node and Postgres versions, browser engine and build type.
  • Put the reasoning in an ADR and link it in Source; add the commit hash once the change is merged.
  • Re-use the existing harnesses where they fit:
    • apps/server/scripts/context-bench.ts (find_context vs the old search + read flow, tokens, calls, success, latency)
    • apps/server/src/context/context.db.test.ts (retrieval assertions and token log lines, patch_section tokens)
    • apps/server/src/context/sectionPatch.test.ts (patch_section concurrency and fuzz)
    • apps/server/scripts/section-write-bench.ts (read_page section / patch_section / update_page replace core latency, no database) and apps/server/src/context/notationRoundTrip.test.ts (element × scenario preservation census)
    • apps/server/src/context/changeFeed.test.ts (changes_since recall and tokens)
    • apps/server/src/collectionQuery/collectionQuery.db.test.ts (query_rows tokens)
    • apps/server/src/perf.test.ts and apps/web/src/lib/perf.test.ts
    • apps/server/scripts/snapshot-chain-bench.ts (version history: a page replayed as N appends, snapshot rows raw / on disk, page_docs size, version preview / compare / restore, store and index pass)
    • apps/server/scripts/large-page-bench.ts (large pages: index coverage, outline/section, append and patch_section latency, event-loop stalls and other requests during the call; --state for a real page)
    • apps/server/scripts/cache-sim.ts (cache replacement: LRU, SIEVE, S3-FIFO and the OPT bound on the same traces and capacities; add a trace before changing a cache's size or policy)
    • apps/server/src/unionFind.test.ts (union-find hop counts on worst-case inputs)
    • apps/server/scripts/mcp-token-bench.ts (tokens an agent receives: 3 agents re-reading with and without known, list_pages json/lines/compact on 2,000 pages, dated folders, search, patch_sections vs patch_section)
    • apps/server/scripts/multi-query-bench.ts and apps/server/src/mcpTools/multiQuery.db.test.ts (find_context with several phrasings vs one call per phrasing: calls, tokens, answer sections)
    • apps/server/src/context/semantic.db.test.ts with the fake endpoint of semanticTestServer.ts (semantic search on and off; off must stay at 0 queries and 0 requests)
    • apps/server/src/teamAgents.test.ts and apps/server/src/teamAgents.db.test.ts (inbox hand-off lines and the catch_up team group, tokens with TOKENS=1)
    • apps/server/src/mcpTools/rowStatus.db.test.ts (status lines after update_row / create_row / query_rows, tokens with TOKENS=1)
    • apps/server/scripts/mcp-tools-list-cost.ts [--profile core|full] [--by-tool] [--surface] [--json] (fixed MCP cost per session: tools/list per profile and per tool, server instructions, and with --surface the initialize result, resource templates and prompts; no database, exact for a build)
    • apps/server/scripts/search-bench.ts (MCP search latency over 1, 5 and 10 workspaces of 5,000 pages, before and after interleaved; scratch database)
    • apps/server/scripts/ai-step-bench.ts [--writes N] (version rows per agent write: rows, raw and on-disk bytes, write latency on a small note and a large log)
    • apps/server/scripts/collection017-bench.ts (page, row, property and section writes with the 0.17 triggers, bulk inserts, query_rows with and without automatic fields)
    • apps/server/src/routes/vaultSyncScale.db.test.ts with VSYNC_SCALE_N=1000 (vault sync both ways, rate limiter off and on)
  • Browser measurements in the existing entries (React commits, long tasks, editor repros) were made with out-of-tree Playwright scripts. Describe the script in the ADR precisely enough to repeat it.
  • Do not round or restate a number differently here than in its source. If the source does not record the conditions, write "conditions not recorded".
